    요약

    레거시 ASP.NET WebForms 라이브러리 Idunno.AntiCsrf에서 CVE-2026-131914 역직렬화 취약점이 발견됐다. 모듈은 CSRF 토큰의 무결성을 검증하지 않은 채 역직렬화하며, 인증 없이 접근 가능한 대상 페이지에서는 단일 POST 요청으로 IIS worker process 권한의 RCE가 가능하다. Mandiant는 실제 악용(in the wild)을 보고했고, The Hacker News는 2026-11-23 이를 보도했다.

    항목 내용
    CVE CVE-2026-131914
    취약점 유형 CWE-502: 신뢰할 수 없는 데이터의 역직렬화
    영향 버전 0.9.1.0, 0.9.1 Beta
    CVSS 4.0 기준 9.3, Critical
    취약 컴포넌트 Idunno.AntiCsrf.AntiCsrfModule
    트리거 대상 WebForms 페이지에 대한 HTTP POST
    실행 컨텍스트 IIS worker process인 w3wp.exe
    patch 상태 공식 patch 없이 사용 중단·대체 권고

    취약 지점과 악용 조건

    취약 지점은 AntiCsrfModule.PreRequestHandlerExecute다. 이 함수는 POST 요청에서 설정된 CSRF 쿠키와 폼 필드가 비어 있지 않은지만 검사한다. 이후 매개변수 없는 ObjectStateFormatter를 생성해 폼 필드 값을 역직렬화하고, 그 결과를 쿠키와 비교한다.

    처리 순서는 다음과 같다.

    1. 요청 핸들러가 System.Web.UI.Page인지 확인한다.
    2. ISuppressCsrfCheck 구현 또는 [SuppressCsrfCheck] 적용 여부를 확인한다.
    3. POST 요청의 CSRF 쿠키와 폼 필드가 비어 있지 않은지 검사한다.
    4. 폼 필드 값을 ObjectStateFormatter.Deserialize()에 전달한다.
    5. 역직렬화 결과와 쿠키 값을 비교한다.

    공격자 제어 데이터가 토큰 비교보다 먼저 역직렬화된다. 이 경로에는 MAC, 서명, machineKey 검증이나 타입 제한이 없다. 따라서 유효한 CSRF 토큰을 몰라도 적절한 gadget chain을 역직렬화 sink에 전달할 수 있다.

    기본 입력 이름은 쿠키 __CSRFCOOKIE와 폼 필드 __CSRFTOKEN이다. 쿠키의 GUID 형식 검사는 렌더링 단계인 PagePreRender에서 수행되며, POST의 역직렬화 진입 전에는 수행되지 않는다. 또한 <csrfSettings> 섹션을 통째로 생략하면 CsrfSettings.DetectionResult의 setter 버그로 폼 필드 이름이 RaiseException으로 덮어써질 수 있다.

    Page_Load의 인증 검사보다 먼저 실행된다

    PreRequestHandlerExecute는 페이지의 PreInit, Init, Page_Load보다 먼저 실행된다. 로그인 여부를 Page_Load에서 검사하는 페이지도 이 경로에 노출될 수 있다. 다만 파이프라인의 AuthenticateRequest와 AuthorizeRequest는 앞서 실행되므로, 해당 단계에서 접근이 차단되는 페이지까지 인증을 우회하는 취약점은 아니다.

    대상 페이지에 <form runat="server">가 없어도 POST 역직렬화 경로에 진입한다. 반대로 ISuppressCsrfCheck를 구현하거나 [SuppressCsrfCheck]가 적용된 페이지는 이 검사 경로에서 제외된다.

    코드 분석

    Abraxas의 공개 재현 분석은 Mandiant advisory의 SHA-256과 일치하는 공식 2008년 DLL에서 다음 호출을 식별했다.

    출처: Abraxas: Idunno.AntiCsrf 역직렬화 재현 분석

    new ObjectStateFormatter().Deserialize(formFieldValue)

    PreRequestHandlerExecute는 CSRF 쿠키와 폼 필드의 비어 있지 않음만 검사한 뒤 이 호출에 도달한다. formFieldValue는 요청에서 가져온 공격자 제어 값이며, 역직렬화 전에 출처와 무결성을 검증하지 않는다. Mandiant가 설명한 RCE primitive는 이 지점에 Base64로 인코딩한 ObjectStateFormatter gadget chain을 전달해 w3wp.exe 안에서 코드를 실행하는 것이다.

    공개 재현은 별도로 생성한 System.Web.UI.Pair 객체를 토큰으로 직렬화한 뒤 동일한 sink 호출로 복원했다. 이는 위조 토큰이 역직렬화된다는 증거이며, gadget chain을 통한 프로세스 실행이나 IIS 전체 요청 흐름의 RCE 재현은 아니다.

    토큰을 발급하는 경로도 같은 formatter를 사용한다. PagePreRender는 GUID 쿠키 값을 ObjectStateFormatter.Serialize()로 직렬화해 숨겨진 폼 필드에 넣는다. 서버가 발급한 값과 공격자가 만든 값을 구분하는 암호학적 검증이 POST 처리 경로에 없다는 점이 핵심이다.

    자산 식별과 탐지 포인트

    서버

    Web.config의 <httpModules>와 <modules>에서 Idunno.AntiCsrf.AntiCsrfModule, Idunno.AntiCsrf 등록을 찾는다. 애플리케이션의 bin/ 디렉터리에서 Idunno.AntiCsrf.dll을 확인하고, <csrfSettings>에 지정된 쿠키·폼 필드 이름과 오류 처리 설정을 함께 점검한다.

    공식 2008년 배포 DLL의 식별값은 다음과 같다.

    항목 값
    어셈블리 버전 0.9.1.0
    파일 크기 69,632바이트
    SHA-256 da1efcfed182597ee946a9ef2895dfdfeab2bdff16855aeef01656d8158ead06

    내부 재빌드나 커스텀 빌드는 해시가 달라도 취약한 호출을 유지할 수 있다. 모듈 등록과 어셈블리 이름을 함께 확인한다.

    네트워크

    IIS 접근 로그에서 .aspx 대상의 비정상 POST를 살핀다. Mandiant가 제시한 분석 단서는 HTTP 302·500 응답과, 기록되는 환경에서의 큰 cs-bytes 값이다. 요청 본문을 보관하는 장비에서는 실제 설정된 CSRF 폼 필드와 비어 있지 않은 CSRF 쿠키를 함께 대조한다.

    HTTP 302나 500만으로 exploit 실패를 판단할 수 없다. 역직렬화 이후 토큰 비교가 실패하면 detectionResult="Redirect" 설정에 따라 오류 페이지로 이동하거나 PotentialCsrfException이 발생한다. 예외가 발생한 경우에도 customErrors 설정에 따라 302 또는 500이 반환될 수 있다.

    엔드포인트

    w3wp.exe의 비정상 자식 프로세스와 웹 루트의 비인가 파일 생성·변경을 요청 시각과 대조한다. 상태 코드와 요청 크기는 조사 대상을 좁히는 단서로 사용하고, 프로세스·파일 기록과 연결해 판단한다.

    대응

    Idunno.AntiCsrf 의존성과 모듈 등록을 제거하고 기존 CSRF 보호 기능을 대체한다. 프로젝트는 2008년 12월 이후 갱신이 중단됐으며 공식 patch가 없다.

    대체 방식은 애플리케이션의 요청 처리 구조에 맞춰 선택한다.

    대체 방식 적용 시 확인할 지점
    System.Web.Helpers.AntiForgery 토큰 발급과 요청 검증을 실제 처리 경로에 연결
    Page.ViewStateUserKey와 MAC 검증된 ViewState WebForms postback 폼에서 사용자별 결합과 검증 적용
    ASP.NET Core IAntiforgery ASP.NET Core 전환 시 토큰 발급·검증 적용

    침해 흔적이 있으면 Web.config와 applicationHost.config에 저장된 <machineKey>, 암호화 키, 데이터베이스 자격 증명을 교체한다. 웹 루트의 비인가 파일과 IIS 프로세스 활동도 함께 조사한다.
