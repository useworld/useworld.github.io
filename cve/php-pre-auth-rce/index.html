    요약

    2026-10-21 공개된 Unit 42 브리핑은 CVE-2026-109618과 CVE-2026-109619를 PHP의 Critical 취약점으로 분류한다. PHP 프로젝트의 GitHub Security Advisory와 구버전용 보안 브랜치도 공개됐지만, 수집된 페이지 본문에는 영향 버전, CVSS, 취약 함수, patch diff, 인증 조건을 확인할 수 있는 기술 내용이 포함되지 않았다.

    따라서 두 문제를 pre-auth RCE로 단정하거나 특정 PHP 버전을 수정 버전으로 제시할 근거는 현재 자료만으로 충분하지 않다. 인터넷 요청을 처리하는 PHP 환경은 advisory 원문과 배포판 공지를 기준으로 영향 여부를 판정하고, 수정 패키지가 제공되면 실행 중인 worker까지 교체해야 한다.

    항목 확인된 내용
    CVE CVE-2026-109618, CVE-2026-109619
    대상 PHP
    공개 분석일 2026-10-21
    심각도 표현 Unit 42가 두 취약점을 Critical로 분류
    공식 자료 PHP 프로젝트의 GitHub Security Advisory 2건
    구버전 자료 PHP 7.4·8.0용 CVE 전용 브랜치 공개
    실제 악용 수집된 자료에서 확인되지 않음
    PoC·patch diff 수집된 본문에서 확인되지 않음

    영향 버전은 배포판 기준으로 확인

    운영체제와 상용 PHP 공급자는 upstream 버전 번호를 유지하면서 보안 patch를 backport할 수 있다. php --version 결과만으로 취약 여부를 단정하지 말고 패키지 changelog와 공급자 advisory를 함께 확인한다.

    영향 확인

    웹 요청을 처리하는 PHP runtime을 우선 조사한다.

    • PHP-FPM
    • Apache mod_php
    • php-cgi
    • LiteSpeed의 PHP worker
    • PHP를 내장하거나 별도 worker로 실행하는 웹 서버와 애플리케이션 플랫폼

    CLI와 웹 서버가 서로 다른 PHP 바이너리 또는 설정을 사용할 수 있다. CLI 버전만 확인하면 실제 요청을 처리하는 FPM pool이나 CGI 프로세스를 놓칠 수 있다.

    Linux

    php --version
php --ini

ps -eo pid,ppid,user,comm,args |
  grep -E 'php-fpm|php-cgi|apache2|httpd|lsphp'

    FPM 설정과 pool별 실행 파일도 확인한다.

    systemctl status php-fpm
systemctl list-units --type=service |
  grep -E 'php.*fpm|apache2|httpd|lshttpd'

    Windows

    php --version
php --ini

Get-Process php-cgi, httpd, nginx, lsphp -ErrorAction SilentlyContinue |
    Select-Object Id, ProcessName, Path, StartTime

Get-CimInstance Win32_Process |
    Where-Object { $_.Name -match '^(php-cgi|httpd|nginx|lsphp)\.exe$' } |
    Select-Object Name, ProcessId, ExecutablePath, CommandLine

    컨테이너 환경에서는 호스트의 PHP가 아니라 실제 서비스 이미지와 실행 중인 컨테이너를 확인한다.

    docker ps --format '{{.ID}} {{.Image}} {{.Names}}'
docker exec <container> php --version

    업데이트

    PHP 프로젝트의 Security Advisory와 사용 중인 운영체제 또는 상용 공급자의 공지에서 수정 버전을 확인한다. PHP 7.4와 8.0용 CVE 전용 브랜치는 공개돼 있지만, 브랜치 존재만으로 해당 계열의 일반 지원이 재개됐다고 해석할 수 없다.

    패키지나 이미지를 교체한 뒤에는 요청을 처리하는 프로세스를 재시작한다.

    systemctl restart php-fpm
systemctl restart apache2
systemctl restart httpd

    서비스 이름은 배포판과 설치 방식에 따라 다르다. 여러 FPM 버전이나 pool을 함께 운영한다면 각각의 master process와 worker가 교체됐는지 확인한다.

    ps -eo lstart,pid,ppid,comm,args |
  grep -E 'php-fpm|php-cgi|apache2|httpd|lsphp'

    컨테이너는 수정된 이미지로 다시 생성한다. 패키지만 갱신하고 기존 컨테이너나 worker를 계속 실행하면 메모리에 적재된 이전 runtime이 요청을 처리할 수 있다.

    임시 노출 축소

    취약점의 구체적인 trigger와 patch 로직이 수집된 자료에서 확인되지 않았으므로 memory_limit, session.upload_progress, fatal_error_backtraces 변경을 공식 완화책으로 간주할 근거는 없다. 임의의 설정 변경은 서비스 장애를 만들거나 공격 표면을 그대로 남길 수 있다.

    업데이트 전에는 PHP가 직접 처리하는 요청의 범위를 줄인다.

    • 외부에 노출할 필요가 없는 PHP endpoint를 reverse proxy 또는 웹 서버에서 차단한다.
    • 업로드 endpoint의 요청 본문 크기와 multipart part 수를 제한한다.
    • 관리용 PHP endpoint는 네트워크 접근 제어 뒤로 이동한다.
    • 불필요한 CGI handler와 사용하지 않는 SAPI를 비활성화한다.
    • PHP worker 권한과 웹 루트 쓰기 권한을 최소화한다.

    요청 크기 제한은 가용성 보호에도 유효하지만, 두 CVE의 exploit을 차단하는 patch를 대신하지 않는다.

    탐지와 조사

    공개된 수집 자료에는 재현 가능한 PoC, 고유한 요청 패턴 또는 IOC가 포함되지 않았다. 특정 HTTP 문자열을 탐지하는 방식보다 PHP worker의 비정상 동작과 같은 시각의 요청을 연결해 조사한다.

    네트워크

    다음 이벤트를 기준선과 비교한다.

    • 평소보다 큰 POST 또는 multipart 요청
    • 단시간에 반복되는 동일 endpoint 요청
    • 비정상적으로 많은 form field나 multipart part
    • PHP 요청 직후 발생한 새로운 외부 연결
    • PHP worker에서 직접 시작된 DNS, HTTP 또는 HTTPS 통신

    요청 크기만으로 exploit을 판정하지 않는다. 같은 시각의 worker crash, 자식 프로세스, 파일 변경을 함께 확인한다.

    엔드포인트

    PHP worker가 생성한 자식 프로세스를 우선 조사한다.

    php-fpm | php-cgi | apache2 | httpd | lsphp
    -> sh | bash | dash | cmd.exe | powershell.exe
    -> curl | wget | certutil.exe
    -> python | perl | node

    추가 확인 대상은 다음과 같다.

    • PHP worker 계정으로 생성되거나 변경된 파일
    • 웹 루트 밖에 기록된 스크립트와 실행 파일
    • 임시 디렉터리에서 실행된 바이너리
    • 서비스 계정의 예약 작업, 시작 프로그램 또는 SSH key 변경
    • PHP worker에서 시작된 shell과 다운로드 도구

    Linux에서는 프로세스 실행과 파일 변경 기록을 조회한다.

    journalctl --since '2026-10-21' |
  grep -Ei 'php|segfault|oom|fatal|killed process'

find /var/www /tmp /var/tmp -type f -newermt '2026-10-21' -ls

    서버

    PHP와 웹 서버 로그에서 다음 사건의 시간 관계를 확인한다.

    • segmentation fault 또는 access violation
    • PHP worker의 비정상 종료와 반복 재시작
    • OOM killer 또는 메모리 제한 오류
    • 요청 직후 발생한 fatal error와 timeout
    • FPM pool의 급격한 worker 교체
    • 웹 서버의 5xx 응답 증가
    journalctl -u php-fpm --since '2026-10-21'
journalctl -u apache2 --since '2026-10-21'
journalctl -u httpd --since '2026-10-21'
dmesg --ctime | grep -Ei 'segfault|oom|killed process|php'

    단일 crash는 exploit의 증거가 아니다. reverse proxy 로그의 요청 시각, PHP 오류, worker 재시작, 자식 프로세스 실행, 파일 변경, 외부 통신을 하나의 타임라인으로 결합한다.
