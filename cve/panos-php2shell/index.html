    PAN-OS 관리면을 노린 PHP2Shell

    PHP2Shell은 PHP의 메모리 오류 처리 취약점인 CVE-2026-109618과 CVE-2026-109619를 가리킨다. 두 취약점은 애플리케이션의 인증 코드가 실행되기 전 요청 처리 경로에서 RCE로 이어진다. Unit 42는 2026-10-29 인터넷에 노출된 PAN-OS 관리 인터페이스에 대한 실제 악용과 대응 patch 제공 사실을 발표했다.
    2026-11-20 # cve

    요약

    PHP2Shell은 PHP의 메모리 오류 처리 취약점인 CVE-2026-109618과 CVE-2026-109619를 가리킨다. 두 취약점은 애플리케이션의 인증 코드가 실행되기 전 요청 처리 경로에서 RCE로 이어진다. Unit 42는 2026-10-29 인터넷에 노출된 PAN-OS 관리 인터페이스에 대한 실제 악용과 대응 patch 제공 사실을 발표했다.

    공격 진입점은 로그인 로직보다 앞에 있는 PHP의 multipart 요청 파서다. 관리 계정의 인증 강화만으로 이 경로를 차단할 수 없다.

    항목 내용
    취약점 CVE-2026-109618, CVE-2026-109619
    명칭 PHP2Shell
    심각도 CVSS 4.0 기준 9.2
    취약 지점 OOM 오류 처리와 요청 종료 후 남는 내부 상태
    공격 형태 pre-auth RCE
    실제 악용 대상 인터넷에 노출된 PAN-OS 관리 인터페이스
    대응 PHP 보안 업데이트 또는 PHP2Shell 대응 PAN-OS firmware 적용

    공개와 악용 타임라인

    날짜 내용
    2026-10-20 조율된 공개에 앞서 취약점 정보가 유출됐다. VulnCheck는 이날 두 취약점을 재현했다고 밝혔다.
    2026-10-21 PHP가 취약점 상세와 긴급 patch를 공개했다.
    2026-10-29 Unit 42가 PAN-OS 관리 인터페이스의 실제 악용과 Linux kernel 권한 상승을 연결한 exploit chain을 발표했다.
    2026-11-19 Unit 42가 PHP의 추가 보안 릴리스 내용을 반영했다. 같은 날 The Hacker News가 PAN-OS 공격의 기술적 배경을 설명했다.

    2026-11-19 PHP 보안 릴리스는 후속 업데이트다. PHP2Shell 최초 patch 공개일인 2026-10-21과 구분한다. Unit 42가 후속 업데이트에서 언급한 비기본 구성 조건을 PHP2Shell 전체의 공격 조건으로 확대해서도 안 된다. VulnCheck는 여러 PHP 버전에서 기본 설정을 사용한 RCE를 재현했다고 밝혔다.

    취약 지점과 공격 흐름

    OOM으로 중단된 요청의 정리

    CVE-2026-109618은 메모리 부족 상태를 처리하는 과정에서 발생한다. PHP가 longjmp()로 실행 흐름을 중단하면 요청 내부 데이터가 부분적으로만 초기화된 채 정리 경로에 들어갈 수 있다. 정리 코드가 이 데이터를 정상 상태로 취급하면서 메모리 손상이 발생한다.

    CVE-2026-109619는 요청이 소유한 메모리가 해제된 뒤에도 전역 상태가 해당 영역을 가리키는 문제다. 같은 worker가 후속 요청을 처리할 때 정상 초기화보다 먼저 이 상태를 읽거나 제어 흐름에 사용하면 RCE로 이어질 수 있다.

    핵심은 OOM 자체가 아니라, 오류 처리 이후에도 유효하지 않은 상태가 사용된다는 점이다.

    multipart 파싱에서 시작되는 트리거

    조작된 multipart 요청은 애플리케이션 코드가 실행되기 전 PHP의 요청 파싱 단계에서 메모리 제한에 도달하도록 구성된다. 깊게 중첩된 빈 파일 필드는 HTTP 본문 크기보다 훨씬 큰 내부 메모리 할당을 유발할 수 있다. 따라서 post_max_size만으로 메모리 고갈 경로를 차단했다고 판단할 수 없다.

    The Hacker News는 기본 post_max_size인 8 MB보다 작은 요청도 기본 memory_limit인 128 MB를 소진할 수 있다고 설명했다. Assetnote scanner 역시 62단계로 중첩된 PHP 배열 키를 사용하는 multipart probe로 이 경로를 검사한다.

    PAN-OS에서의 코드 실행과 권한 상승

    Unit 42는 PAN-OS 관리 인터페이스에서 PHP2Shell을 악용한 뒤 Linux kernel 권한 상승 취약점을 연결한 공격을 설명했다. Dream Research가 보고한 공격 도구를 독립적으로 검증하고 결과도 재현했다고 밝혔다. PHP worker 문맥의 RCE와 root 권한 획득은 별도 단계다.

    exploit의 동작 조건은 PHP 빌드, 아키텍처, 메모리 배치에 따라 달라진다. VulnCheck는 2026-11-10 기준 PAN-OS 12.2.3의 ARM64와 PAN-OS 11.2.0의 AMD64에서 RCE를 재현했다고 밝혔다. 이는 재현한 조합이며, PAN-OS 전체의 영향 범위를 뜻하지 않는다.

    PoC 분석

    공개 PoC의 poc_109618.py는 다음 함수로 multipart 본문을 구성한다.

    출처: eness — PHP2Shell PoC

    def build_multipart(parts, boundary: bytes) -> bytes:
    out = bytearray()
    for p in parts:
        name = p["name"].encode()
        out += b"--" + boundary + b"\r\n"
        out += b'Content-Disposition: form-data; name="' + name + b'"'
        if p.get("filename") is not None:
            out += b'; filename="' + p["filename"].encode() + b'"'
            out += b"\r\nContent-Type: application/octet-stream"
        out += b"\r\n\r\n" + p["data"] + b"\r\n"
    out += b"--" + boundary + b"--\r\n"
    return bytes(out)

    이 함수는 각 part의 name, 선택적 filename, 데이터를 직렬화해 PHP의 multipart 업로드 처리 경로로 전달할 본문을 만든다. 메모리 고갈을 유발하는 part 구성과 메모리 손상 이후의 제어 흐름 전환은 별도 로직에 달려 있다. 이 함수만으로 RCE가 성립하는 것은 아니다.

    저장소는 session upload progress 처리 함수인 php_session_rfc1867_callback()과 ext/session/session.c를 분석 대상으로 제시한다. 설명에 따르면 post_bytes_processed와 current_file_bytes_processed는 HashTable bucket 내부의 zval *를 보관한다. 진행률 갱신 중 zend_hash_update()가 기존 데이터 트리를 zval_ptr_dtor로 해제하면 이 포인터가 해제된 메모리를 계속 가리킬 수 있다.

    저장소가 설명하는 exploit primitive는 해제된 bucket 메모리를 재사용해 조작된 zend_fcall_info와 zend_internal_function 구조체로 연결하고, zend_call_function() 호출을 코드 실행으로 전환하는 것이다. 이 upload progress 경로의 설명을 두 CVE의 모든 트리거에 그대로 적용해서는 안 된다.

    PoC는 zval_ptr_dtor와 zend_call_function 사이의 심볼 offset 등 빌드별 정보를 사용한다. VulnCheck도 검증한 공개 PoC 하나가 PHP 8.4.26의 특정 구성에서만 ASLR을 우회했다고 밝혔다. 공개 PoC의 성공 여부와 제품의 취약 여부는 구분해야 한다.

    영향 범위와 patch

    일반 PHP의 수정 버전과 PAN-OS firmware의 수정 여부는 따로 판단한다. 장비에 표시되는 PHP 버전만으로 벤더 backport 적용 여부를 판정하지 않는다.

    PHP 계열 PHP2Shell 수정 버전
    PHP 8.2 8.2.35
    PHP 8.3 8.3.36
    PHP 8.4 8.4.27
    PHP 8.5 8.5.12

    VulnCheck는 위 버전을 수정 버전으로 제시한다. PHP 8.1 이하 계열은 공식 지원이 종료됐으므로 배포판의 보안 유지보수 여부를 점검하거나 지원 중인 버전으로 전환한다.

    session.upload_progress.enabled=0은 CVE-2026-109619에 대해 제시된 완화 설정이다. 요청 파싱 전에 적용되는 php.ini, FPM pool 또는 서버 설정에서 지정하고 모든 worker를 재시작해야 한다. 애플리케이션 코드의 ini_set()은 요청 파싱 이후에 실행되므로 같은 효과를 기대할 수 없다.

    CVE-2026-109618에 대한 임시 완화는 별개다. VulnCheck가 인용한 PHP 지침은 memory_limit=-1로 제어 가능한 PHP 메모리 제한 실패를 제거하는 방법을 설명하지만, 하위 메모리 할당 실패까지 제거하지는 못한다. 요청 크기 제한도 multipart part 수와 중첩 깊이, 유효한 Content-Length가 없는 요청까지 고려해야 한다.

    PAN-OS 관리면 접근 제한과 patch

    인터넷에서 관리 인터페이스로 직접 접근하는 경로를 제거하고 신뢰하는 내부 IP로 접근을 제한한다. PHP2Shell 대응 PAN-OS firmware를 적용한다. Unit 42는 해당 수정본이 관측된 exploit chain을 차단한다고 밝혔다.

    탐지와 침해 조사

    네트워크

    PAN-OS 관리 인터페이스로 들어온 multipart POST와 직후의 오류 응답을 연결한다. 로그인 성공 여부보다 요청의 Content-Type, multipart 필드의 중첩, 반복 요청과 응답 변화를 살핀다.

    Assetnote scanner는 정상 대조 요청과 최대 세 번의 multipart probe를 비교한다. 기본 검사 경로는 /index.php이며, 이는 scanner의 기본값이지 PAN-OS의 특정 취약 엔드포인트를 뜻하지 않는다.

    서버

    multipart 요청 직후 발생한 PHP 메모리 고갈 오류, 빈 HTTP 500 응답, PHP-FPM worker 종료·재시작을 시간순으로 연결한다. 최초 5xx 응답이나 일반적인 요청 거부 응답만으로 worker crash를 판정하지 않는다.

    빈 HTTP 500도 취약점의 확정 증거는 아니다. Assetnote는 patch된 PHP 8.4.27의 낮은 memory_limit 설정과 특정 multipart 제한을 적용한 PHP 8.3.36에서도 같은 응답이 발생했다고 설명한다. 오류 응답은 설치 버전과 벤더 backport 적용 여부를 함께 대조한다.

    엔드포인트

    Unit 42의 hunting query는 PHP 웹 서버 또는 worker 문맥에서 시작된 후속 명령 실행을 찾는다. php-fpm, php-cgi, httpd, apache2에서 파생된 shell과 예상 밖 인터프리터 실행을 살핀다.

    관측 지점 연결할 기록
    관리면 접근 외부 출발지의 multipart POST와 오류 응답 시각
    PHP 및 서비스 메모리 고갈, worker 종료·재시작과 요청 시각
    프로세스 웹 서버·PHP worker의 자식 프로세스, 실행 계정, 명령행
    권한 변화 코드 실행 이후의 비정상 권한 상승과 root 프로세스 실행

    이 프로세스 탐지 방식은 PHP2Shell 전용이 아니다. 서비스가 평소 실행하는 명령과 비교하고, 요청·오류·프로세스 기록이 같은 흐름으로 이어지는지 확인한다. patch 적용 후에도 외부에 노출됐던 기간의 기록을 조사한다.
